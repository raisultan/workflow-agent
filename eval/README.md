# Eval services

Local, synthetic stand-ins for the systems the workbench talks to, so a job can run end to end with no outside writes (`T11.7`).
Nothing here is a real account; every password and token is generated by `bootstrap.ts` into `eval/.state/` (git-ignored, mode
0600) and never printed.

| Service | What it is | Address on the host |
| --- | --- | --- |
| Mattermost 9.11 | A real Mattermost with synthetic people `dev-ivan` (ivan@example.test) and `lead-1` (lead@example.test), the bot `workbench`, team `engineering`, and channels `orders-node` and `orders-python` | `127.0.0.1:8065` |
| Mock Jira | [`services/mock-jira.ts`](services/mock-jira.ts): the Jira REST v2 subset the connector uses, with the synthetic `ORD-*` issues and the same people, with the same emails | `127.0.0.1:25411` |
| Mock GitLab | [`services/mock-gitlab.ts`](services/mock-gitlab.ts): the REST subset the connector uses, git's smart HTTP over bare repositories, and pipelines scripted per project | `127.0.0.1:8929` |

The mock GitLab serves the repositories under [`repos/`](repos): each directory with a `mock.json` (`project`, and its `ci` script)
becomes a project. Its repositories live in a `tmpfs`, so every start is fresh. The connector's contract tests
([`tests/gitlab-contract.spec.ts`](../tests/gitlab-contract.spec.ts)) run against the same mock in `pnpm check`.

## Start

```bash
node eval/bootstrap.ts
docker compose -p workbench-eval -f eval/docker-compose.yml --env-file eval/.state/services.env up -d --build
node eval/bootstrap.ts --provision
```

`--provision` writes `eval/.state/workbench.env`: the connector settings for the workbench's container (the services at
`host.docker.internal`), the two channel ids, and the allowed senders.

## Run the workbench against them

```bash
set -a; . eval/.state/workbench.env; set +a
export LITELLM_MODEL=deepseek-flash   # plus DEEPSEEK_API_KEY and LITELLM_BASE_URL for the model
docker compose -p workbench-eval-run -f docker-compose.yml -f eval/workbench.compose.yml --profile full up -d --build
```

[`workbench.compose.yml`](workbench.compose.yml) mounts [`profile.cordis.patch.yml`](profile.cordis.patch.yml), which configures the
two repositories: a job started in `orders-node` works on `eval/orders-node`, one in `orders-python` on `eval/orders-python`. Each
lists `lead@example.test` as its approver (`D12`), so only `lead-1` approves, and a plan is approved with a comment in its Jira ticket.

Talk to it as a synthetic person, and read a thread back:

```bash
node eval/post.ts dev-ivan orders-python "@workbench сделай ORD-201"
node eval/post.ts --read <post id>
```

Script CI, post a review note, or merge, through the mock GitLab's control API (`<project>` URL-encoded, as `eval%2Forders-node`; the token is `EVAL_GITLAB_TOKEN` in
`eval/.state/services.env`): `POST /__mock/projects/<project>/ci` with `{ "runs": [{ "status": "failed" }], "default": { "status": "success" } }`,
`POST /__mock/projects/<project>/merge_requests/<iid>/notes` with `{ "body": "…", "author": { "username": "lead-1" } }`,
`POST /__mock/projects/<project>/merge_requests/<iid>/merge`, and `GET /__mock/state`. Comment on a Jira ticket as a person (the
form under each ticket at `127.0.0.1:25411` does the same): `POST /rest/api/2/issue/<key>/comment` with `{ "author": "lead-1", "body": "ок" }`.

## End-to-end eval

`pnpm eval:e2e` ([`e2e.ts`](e2e.ts), `T13.3`) runs each scenario of [`scenarios.ts`](scenarios.ts), twice by default, as a real-model
job through a workbench of its own, and plays the people: `dev-ivan` starts each run and answers its questions, `lead-1` approves the
plan in the Jira ticket. Each run gets its own GitLab project, repository profile, Jira ticket and Mattermost thread. When a job ends,
the scenario's hidden tests ([`hidden/`](hidden/README.md)) run on its merge request's branch.

It needs the services above started and provisioned, a built image (`workflow-agent:local`), and a model:

```bash
LITELLM_BASE_URL=https://api.deepseek.com/v1 LITELLM_API_KEY=sk-your-key pnpm eval:e2e
pnpm eval:e2e --scenarios s01,s09 --runs 1    # some scenarios, once
pnpm eval:e2e --check-hidden                  # no model: the hidden tests must fail on each scenario's starting code
pnpm eval:e2e --setup-only                    # a dry run: projects, tickets, profile and the workbench, no jobs
```

The model is `EVAL_MODEL`, else `model` in [`e2e.config.json`](e2e.config.json) (`deepseek-flash`), which also holds the prices the
report's cost uses. Other options: `--concurrency` (2), `--project` (the Compose project, `workflow-agent-eval`) and `--image`.
The reports are `eval/.state/e2e/report-<time>.json` and `.md`: per job, its outcome, the hidden tests' result, stages and attempts,
gates and questions, check failures, refused connections, tokens and cost. It calls a real model and starts containers, so it is
manual and not part of `pnpm check`.

## Stop

```bash
docker compose -p workbench-eval -f eval/docker-compose.yml --env-file eval/.state/services.env down
```
